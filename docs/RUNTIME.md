# Submux Runtime 目标设计

> 状态：已接受的目标架构，正在实现。仓库已经包含 Runtime 的核心部署基础、本机 IPC、单实例锁、单写者状态库、可恢复的持久化运行操作、可靠事件流、分层候选配置预览、托管资源、本机高级覆盖、显式代理配置应用、三类配置来源、多来源原子切换和来源级 Mihomo 状态隔离，以及共用 IPC 的 CLI、Bubble Tea TUI 和 Tauri GUI；TUN/网关模式、安装脚本和发布产物仍在开发中，当前代码不能作为可部署的 Runtime 实现。

## 定位

Submux Runtime 是独立安装在本机的 Mihomo 管理程序。submux 只生成并发布输出订阅；Runtime 可以把输出订阅当作一种配置来源，但不向 submux 注册，不建立设备身份，不发送心跳，也不接受由 submux 发起的运行操作。

一台机器或一个网络命名空间只运行一个 Submux Runtime，一个 Runtime 只管理一个 Mihomo。GUI、TUI 和 CLI 只通过本机 IPC 管理 Runtime，Mihomo 控制接口不向这些客户端直接开放。

```text
submux 输出订阅 ──┐
外部 HTTP(S) 配置 ─┼─> Runtime 配置来源 ─> 本机覆盖与校验 ─> 一个 Mihomo
本机导入副本 ─────┘                              │
                                               ├─ 显式代理
GUI ─┐                                         ├─ TUN
TUI ─┼─ 本机 IPC ─> Submux Runtime ────────────└─ Linux 网关
CLI ─┘                    │
                          └─ 受限内部 IPC ─> 特权网络进程
```

硬约束如下：

1. Runtime 没有 submux 设备身份、配对、心跳、WSS、由 submux 发起的运行操作或远程管理入口。
2. 本机管理不监听 TCP；Unix Socket 和 Windows Named Pipe 是唯一外部管理入口。
3. 运行方式只能是显式代理、TUN 或 Linux 网关，任意时刻只使用一种。
4. TUN 和网关发生故障时恢复直连，不提供故障阻断或 kill switch。
5. 配置来源不能扩大 Runtime 的系统权限、监听范围或文件访问范围。
6. 产品、Runtime 和 Mihomo 的安装都不能由配置来源触发。
7. 不迁移、导入或探测任何已移除的远程运行端状态。用户负责在安装前清理旧软件，Runtime 安装器只判断 Runtime 自身是否存在。

本机 IPC、网络接管和发行安装分别见 [RUNTIME-IPC.md](RUNTIME-IPC.md)、[RUNTIME-NETWORK.md](RUNTIME-NETWORK.md) 与 [RUNTIME-DISTRIBUTION.md](RUNTIME-DISTRIBUTION.md)。

## 程序组成

| 程序 | 默认权限 | 职责 |
|---|---|---|
| `submux-runtime` | 专用低权限系统账户 | 保存状态、管理配置来源、生成候选配置、串行执行运行操作、管理 Mihomo、提供 CLI 与 TUI、本机 IPC |
| `submux-runtime-gui` | 当前桌面用户 | 提供窗口、托盘、通知和首次配置向导，只调用 Runtime 本机 IPC |
| `submux-runtime-net` | Linux/macOS root 或 Windows LocalSystem | 执行固定类型的 TUN、路由、DNS、防火墙和 Linux 网关操作；平台确有需要时按固定规则启动经过验证的 Mihomo |
| Mihomo | 能低则低 | 执行实际代理；只接受 Runtime 生成的有效配置和本机受保护的控制连接 |

`submux-runtime` 同时包含 daemon、CLI 和 TUI，不为 CLI 或 TUI 再增加独立二进制：

```text
submux-runtime serve
submux-runtime tui
submux-runtime status --json
submux-runtime source add --type submux_output <url>
submux-runtime source import --name local-copy <file>
submux-runtime source switch [--use-cache] <source-id>
submux-runtime source delete [--confirm-current] <source-id>
submux-runtime resource add --name provider --kind proxy-provider-yaml <file>
submux-runtime override set <file>
submux-runtime proxy preview --source-id <source-id> [--override-content-id <content-id>]
submux-runtime operation wait <id>
```

在交互式终端直接运行 `submux-runtime` 时进入 TUI；标准输入或输出不是终端时，不隐式进入交互界面。

GUI 使用 Tauri 2。TUI 使用 Bubble Tea v2、Bubbles v2 和 Lip Gloss v2。三种客户端必须具备相同的 Runtime 管理能力；GUI 可以提供向导和图形预览，但不能拥有独占操作。

## 对外接口

Runtime 对客户端只提供三个概念上的接口：

```text
Observe()                 -> Snapshot
Execute(Action, revision) -> Operation
Watch(cursor)             -> Event stream
```

客户端不需要了解配置文件落盘、Mihomo 重载、路由应用、失败恢复或更新安装的内部步骤。读取同步返回快照；所有修改先持久化为运行操作，再由 Runtime 串行执行。客户端退出不会取消已经开始的操作。

同一时刻可以有多个观察客户端，但只能执行一个修改操作。新操作进入有界队列，队列已满时返回忙碌。修改请求必须携带客户端所依据的 Snapshot revision；revision 已变化时拒绝修改并返回最新 revision，不采用最后写入覆盖。

当前实现把排队操作、执行阶段、取消者和终态写入 `runtime.db`。Runtime 重启后继续执行尚未开始的排队操作；中断的执行中操作转为 `outcome_unknown`，不会自动重放。事件使用持久化的单调游标和 NDJSON 流向多个客户端广播；游标过期时客户端先读取新 Snapshot，再从它的最新游标继续观察。运行操作按三十天或 2000 条清理，事件默认保留最近 10000 条；排队、执行中、结果未知和当前故障相关记录不参与自动清理。

完整协议见 [RUNTIME-IPC.md](RUNTIME-IPC.md)。

## 配置来源

Runtime 可以保存多个配置来源，但只有一个当前来源：

1. submux 输出订阅；
2. 独立的 HTTP(S) Mihomo 完整配置地址；
3. 用户明确导入并由 Runtime 保存的本机副本。

Runtime 不监视任意本机文件。导入文件后保存的是 Runtime 自己的副本，原路径不再参与运行。来源之间不会自动切换；当前来源刷新失败时继续使用最近可用配置。

配置按固定顺序生成：

```text
来源原文
  -> 本机高级覆盖
  -> 本机运行设置与 Runtime 保留字段
  -> 候选配置
```

来源原文始终保留，应用覆盖不会回写来源。本机高级覆盖使用 YAML，可以修改 Mihomo 的普通代理行为，但不能修改 Runtime 保留字段。

Runtime 保留至少以下字段：

- Mihomo 控制端点、控制密钥和工作目录；
- 核心与状态文件路径；
- mixed、HTTP、SOCKS、redir、TProxy、DNS 等监听地址与认证；
- 当前运行方式、TUN 设备、路由、DNS 和防火墙相关设置；
- Linux 网关的接管范围、接口、端口和 IPv6 策略；
- 核心、UI 或其他可执行内容的下载与更新地址。

配置预览必须显示每个最终字段来自来源、本机高级覆盖还是 Runtime 保留设置，并明确标出被忽略或替换的来源字段。

## 安全配置范围

来源和本机高级覆盖可以保留节点、策略组、规则、DNS 上游、嗅探和其他普通 Mihomo 能力，但不能借配置访问任意本机路径、创建额外监听、写入系统目录或下载可执行内容。

文件引用遵循以下规则：

1. provider 路径改写到 Runtime 的托管资源目录；
2. `type: file`、证书、密钥和其他文件引用只能指向 Runtime 操作员明确导入的托管资源；
3. `external-ui`、`external-ui-url`、任意核心更新地址和任意写路径被拒绝；
4. 未知的新路径、监听或下载字段默认拒绝，只有 Runtime 的版本化安全策略明确支持后才允许；
5. 来源和高级覆盖不能修改 Runtime 保留字段。

托管资源按内容保存，具有硬性单文件和总量上限。导入时拒绝符号链接、Windows reparse point、路径穿越和类型不符的文件。Runtime 不继承进程环境里的 `SAFE_PATHS`；静态校验和启动 Mihomo 时，只把重新验证过的托管资源目录加入该变量。

## 来源下载

默认只允许校验证书的 HTTPS。HTTP 默认只允许回环地址，其他 HTTP 地址必须按来源明确放行。每个来源可以保存自己的兼容设置：

- 允许私网或回环目标；
- 允许 HTTP；
- 保存 HTTP 凭据；
- 使用导入的自定义 CA；
- 明确跳过 TLS 校验；
- 在全局硬上限内调整超时和响应大小；
- 选择直连或经过当前 Mihomo 下载。

这些设置不能由来源内容自行开启。来源主机名或地址变化时，与目标绑定的私网、HTTP 或跳过 TLS 授权失效，必须重新确认。

无论兼容设置如何，以下限制不能关闭：

- 只接受 HTTP 和 HTTPS；
- 始终阻止 `169.254.0.0/16`、`fe80::/10`、`100.100.100.200/32`、`168.63.129.16/32`、`fd00:ec2::254/128` 和 Runtime 维护的云元数据主机名；
- 不跨来源转发认证头、Cookie 或 URL 凭据；
- HTTPS 不自动降级为 HTTP；
- 重定向次数、压缩前后大小和下载时间存在硬上限；
- 每次解析和连接前重新检查目标地址，防止 DNS 重绑定。

私网或回环授权绑定到规范化的 scheme、host 和 port。每次重定向都重新执行地址检查和授权判断；目标的 scheme、host 或 port 改变时不能沿用原凭据。跳过 TLS 校验是持久但醒目的单来源高风险设置，每次编辑或诊断都显示其状态，后台刷新不能自行开启。

来源默认直连下载，也可以明确选择经过当前 Mihomo；失败时不静默切换线路。手动刷新可以选择只对本次操作使用另一条线路，操作记录保存线路选择但不保存凭据。

## 刷新和切换

只有当前远程来源自动刷新。默认间隔为六小时并加入 ±10% 抖动；每个来源可以设置为 15 分钟至 7 天或关闭。请求使用 ETag 和 Last-Modified。

失败后的重试间隔依次为 1 分钟、5 分钟、15 分钟和 1 小时，并且不超过正常刷新间隔。合理的 `Retry-After` 优先。手动刷新绕过失败退避，但仍受本机短时间防抖限制。网络恢复后加入随机延迟，避免大量机器同时请求。

当前实现已经支持 `submux_output`、`remote_http` 和 `local_import` 三类来源并存，按保存线路或一次性线路刷新远程来源，导入托管资源，保存本机高级覆盖，查看分层字段来源，以及从 CLI、TUI 或 GUI 选择、预览、切换和删除来源。添加、刷新、资源导入和覆盖编辑不会应用配置或启动 Mihomo；首次应用仍保持停止，操作员需要另行执行启动。

切换当前来源时：

1. 远程目标先刷新并生成候选配置；
2. 刷新失败但存在缓存时，必须由操作员明确选择“使用缓存”；
3. 候选配置通过应用和健康检查后，才提交当前来源；
4. 失败时保持原当前来源和运行状态；
5. 不改变本机运行方式；
6. 策略组选择和 provider 缓存按来源隔离；
7. fake-IP 状态只在兼容时保留，DNS 方式或地址范围变化时清理。

当前来源在 Runtime 运行时不能直接删除。操作员必须先切换来源，或者停止 Runtime 后确认删除。

实现中每个来源使用独立的 Mihomo 数据目录，因此策略组选择、provider 缓存和 fake-IP 状态不会跨来源复用。切换操作先准备目标来源：远程来源必须尝试刷新，本机来源读取已经校验的不可变副本；只有操作员提交 `use_cached` 时，远程刷新失败才可以退回该来源最近一次通过校验的缓存。目标配置完成静态校验、应用和健康检查后才以比较并交换方式提交当前来源。任一步失败都会恢复旧配置、旧来源数据目录、旧当前来源和原先的运行或停止状态；当前来源刷新失败本身不会触发切换。

## 配置应用

每次下载或编辑都先生成不可变候选配置：

1. 完成格式、安全字段和托管资源校验；
2. 使用准备运行的 Mihomo 精确版本执行 `mihomo -t -f`；
3. 计算候选配置摘要并保存；
4. 普通配置变化优先通过本机 Mihomo 控制连接热重载；
5. 运行方式、监听、控制端点、数据路径或核心版本变化时执行受控重启；
6. 检查控制连接、必要监听、TUN 或网关状态，并观察短暂稳定期；
7. 成功后把候选配置记为最近可用配置；
8. 失败时恢复上一份最近可用配置。

健康检查只观察本机事实，不依赖公共网站或固定外部 URL。配置错误不能切换来源，也不能覆盖最近可用配置。

Mihomo 控制连接只使用 Unix Socket 或 Windows Named Pipe。Runtime 不为控制接口开启 TCP 监听。

## 状态和存储

Runtime 使用单写者模型：只有 `submux-runtime` 打开数据库，所有客户端通过 IPC 访问。

状态分为两类：

- bbolt `runtime.db` 保存来源元数据、本机设置、期望运行状态、运行操作、事件游标、版本和迁移状态；
- 内容寻址的不可变文件保存来源原文、候选配置、有效配置、最近可用配置和托管资源。

写入顺序是先完整写入并同步候选文件，再用数据库事务提交指针。数据库升级前创建备份；升级或启动验证失败时恢复原程序和数据库备份。

配置正文和凭据默认不额外加密。这是第一版的明确取舍：本机管理员本来就能读取进程和文件，额外密钥托管会增加恢复复杂度，但不能替代操作系统权限边界。状态目录只允许 Runtime 账户和系统管理员读取，目录和文件分别使用仅账户可访问的权限；Runtime 操作员通过 IPC 管理。普通快照、事件、日志和操作记录只包含脱敏地址。操作员必须执行明确的“显示或复制原始地址”操作才能取回完整内容；CLI 需要 `--reveal`，并只记录执行者和时间，不记录秘密。

## 期望运行状态与崩溃恢复

操作员明确启动或停止后，Runtime 保存期望运行状态。系统重新启动时，Runtime 先使用本机最近可用配置恢复，再在刷新到期时更新来源。

Mihomo 异常退出后立即触发故障放行，并采用有限重启：

1. 十分钟内最多自动重启三次；
2. 等待时间为 5 秒、30 秒和 2 分钟；
3. 连续稳定运行十分钟后清零计数；
4. 超过上限后进入“需要处理”，保持直连，不再无限重启；
5. 手动启动、应用新的有效配置或安装新的核心版本可以清除该状态；
6. 内容完全相同的来源刷新不能清除该状态；
7. 机器重启后只尝试一次，失败则恢复“需要处理”。

Runtime 主进程由系统服务管理器恢复。特权网络进程必须独立执行清理，使 Runtime、Mihomo 或特权进程任一异常退出时都尽量恢复直连。

## 首次配置

安装完成后 Runtime 服务可以启动，但 Mihomo 保持停止，也不修改路由和 DNS。首次配置流程如下：

1. 在线安装通过固定官方来源直连下载 Mihomo；无法直连时使用包含核心的完整离线包；
2. 添加远程来源或导入本机配置副本；
3. 生成候选配置并完成静态校验；
4. 选择运行方式；桌面 GUI 推荐 TUN，但必须明确批准系统网络改动，服务器与终端流程默认显式代理；
5. 预览监听、认证、路由、DNS 和网关范围；
6. 操作员明确执行“应用并启动”。

添加来源成功不会自动启动 Mihomo。首次启动成功后才保存期望运行状态。任何一步失败都保持停止且不改变系统网络，可以退出后继续。

不提供一次性导入码、`submux-runtime://` 协议或浏览器深链。submux 页面只需要复制输出订阅地址，GUI、TUI 或 CLI 直接添加该地址。

## 客户端行为

GUI、TUI 和 CLI 均支持：

- 来源添加、编辑、刷新、切换和删除；
- 配置来源、本机高级覆盖和最终配置预览；
- 运行方式与本机网络设置；
- 启动、停止、重启、核心更新和回滚；
- 产品检查更新、手动安装、离线包导入；
- 状态备份、恢复、日志和诊断包；
- 运行操作查询、等待和有限取消。

GUI 的 Tauri 后端调用本机 IPC，WebView 页面不能直接连接 Runtime 或 Mihomo。每个获授权的桌面用户都可以启用自己的托盘程序。托盘默认随该用户登录启动但不弹出主窗口；关闭窗口只隐藏到托盘，“退出 GUI”只退出界面，不停止 Runtime、Mihomo、TUN 或网关。

托盘显示当前运行方式、核心状态和可用更新，并提供打开、刷新、启动、停止和退出 GUI。通知只用于错误、需要重新认证、回滚和需要确认的更新，不发送一般状态噪声。无桌面环境的 Linux 不安装或启动 GUI。

## 操作员与审计

Runtime 不建立自己的账号、密码或角色。操作系统用户组和 IPC 权限是唯一授权来源；进入 Runtime 操作员组的用户拥有完整管理权限。

每个修改操作记录：

- Linux/macOS UID 或 Windows SID；
- 客户端类型和版本；
- 请求 ID、开始和结束时间；
- 操作类型、阶段、结果和脱敏错误。

审计记录不包含输出订阅 token、密码、完整配置或其他秘密。不同操作员看到相同的机器状态和运行操作。

## 日志、事件与诊断

默认保留：

- Runtime 日志七天或 50 MiB；
- Mihomo 日志七天或 50 MiB；
- 运行操作三十天或最多 2000 条；
- 最近 10000 个事件；
- 每个来源最近一次下载的来源原文、最近可用配置和最近三份成功配置；
- 当前使用的 provider 与规则缓存。

时间和大小任一达到上限就清理较旧内容。进行中、结果未知和当前故障相关操作不能自动删除。调试日志默认三十分钟后恢复普通级别，延长必须再次确认。手动清理不能删除当前来源最近一次下载的原文、最近可用配置或正在执行的操作。

Runtime 不发送遥测、崩溃报告或后台诊断。诊断包只由操作员手动生成，先显示内容预览并默认脱敏；原始配置、完整日志和系统网络信息必须逐项选择。诊断包只保存到本机，不提供上传按钮。

## 备份、恢复和卸载

便携备份包含：

- 配置来源和凭据；
- 本机高级覆盖；
- 托管资源；
- 最近可用配置；
- Runtime 自己的状态版本信息。

备份不包含日志、运行操作、缓存、核心二进制、系统服务账户、操作员组或系统网络权限。备份默认为明文，创建时警告并使用仅所有者可读权限；第一版不提供备份加密。

恢复不做合并。Runtime 先备份当前状态，再整体替换；核心默认保持停止。机器相关的监听、TUN、网关和网络设置恢复为“待确认”，不能在另一台机器自动启用。

卸载默认保留状态目录。只有显式选择清除数据时才删除 Runtime 状态；卸载前必须停止接管并恢复系统网络。

## 验收边界

新 Runtime 只有满足以下条件后才能发布：

1. submux 控制面不再包含设备注册、配对、心跳、WSS、由 submux 发起的运行操作和运行实例管理入口；
2. GUI、TUI 和 CLI 的全部修改都经过同一个本机 IPC 接口；
3. 一台机器不能启动第二个 Runtime 或第二个受管 Mihomo；
4. 三种运行方式及其权限、冲突和故障放行均有自动化和真实系统测试；
5. 配置来源不能创建未授权监听、引用任意文件或改变系统网络字段；
6. 候选配置失败、Runtime 崩溃、Mihomo 崩溃和更新失败都能恢复最近可用配置或直连；
7. 在线与离线安装使用相同的签名验证和回滚规则；
8. 日志、快照、事件、操作记录和诊断包经过秘密扫描；
9. 文档、二进制、服务、Socket、Named Pipe 和安装包中不再使用历史产品名；
10. 已移除的远程运行端状态不会被读取、迁移或误认为 Runtime 安装。
